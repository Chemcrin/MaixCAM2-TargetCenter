# 识别链路四层分层方案

**状态：方案，尚未实施。** 本文只定义边界与迁移顺序，不改任何代码。

分层要解决的问题不是"文件太多"，而是**改一处不知道会影响谁**。四层按三个问题划界：
有没有副作用、有没有跨帧状态、是否依赖像素细节。

## 1. 四层定义

| 层 | 职责 | 判据（满足全部才算本层） |
|---|---|---|
| 轮询层 | 取帧、转灰度、投递 | 不产生判据、不持有跨帧状态、不碰硬件与屏幕 |
| 逻辑层 | 流程编排与状态机：何时检测、结果是否可信、优先级仲裁、故障判定 | 可以持有状态；不碰像素细节；不直接产生副作用 |
| 算法层 | 基础算法：模糊、二值化、轮廓过滤、几何 | 纯函数：输出只由入参决定，无状态、无 I/O、不读全局 |
| 执行层 | 输出结果：绘制图像、发串口、下发脉冲、停机、日志 | **唯一允许产生副作用的地方** |

依赖方向只有三条，且不可反向：

```
轮询层 ──帧+时间戳──► 逻辑层 ──调用──► 算法层
                        └──结果/命令──► 执行层
```

硬规则：算法层不得 import 逻辑层或执行层；执行层不得 import 逻辑层（只接收值，不回查状态）。

## 2. 现状盘点

### 轮询层

| 现有符号 | 位置 | 处理 |
|---|---|---|
| `to_gray(img, image_module)` | `camera_source.py` | 留在轮询层 |
| `to_gray_frame(gray)` | `rectangle_center.py` | **应移入轮询层**：它做的是输入边界校验，不属于识别算法 |
| `_capture_loop` 的读帧段 | `app_runtime.py` | **轮询循环实际在这里**：`cam.read` → `to_gray` → `worker.submit`。分层后应抽成 `FramePoller` |
| `LatestFrameWorker.submit` | `vision_worker.py` | 属于轮询层的搬运机制，可原样保留 |

必须点明的事实：`camera_source.py` 只做"帧 → 灰度"的**转换**，真正的**轮询**在 `app_runtime`。
若只把 `camera_source` 当作轮询层，这一层是空的。

### 逻辑层

| 现有符号 | 处理 |
|---|---|
| `RectangleCenterDetector.__init__ / reset / process` | 单帧流程编排，留在逻辑层 |
| `fail_result` / `success_result` / `locate_result` / `finish_result` | 结果判定与字段收口，留在逻辑层 |
| `VisionControl.__init__` | 组件装配，留在逻辑层 |
| `VisionControl.process` | 检测 → 光斑 → 偏差 → 新鲜度门，留在逻辑层（但不再直接发串口） |
| `VisionControl.accept_result` | 新鲜度门与分发，留在逻辑层 |
| `VisionControl.idle` / `status` | 留在逻辑层 |
| `VisionControl._degree_scales` / `_with_heading` | IMU 前馈策略，留在逻辑层 |
| `VisionControl._control` 的**决策段** | 优先级仲裁、状态推进、故障判定——留在逻辑层 |

### 算法层

| 现有符号 | 处理 |
|---|---|
| `blur_frame` / `binarize_frame` | 纯函数，移入算法层 |
| `find_quad_candidates` / `select_largest` | 纯函数，移入算法层 |
| `signed_area` / `order_quad` / `line_cross` / `quad_diagonal_center` | 纯函数，移入算法层 |

这六个函数已经满足"无状态、无 I/O、只吃入参"，搬迁零风险。

### 执行层

| 现有符号 | 处理 |
|---|---|
| `draw_result` | 输出图像，移入执行层 |
| `send_uart(uart, result)` | 输出串口，移入执行层 |
| `_stop_motion` | 硬件动作，移入执行层 |
| `_notice` | 日志/UI，移入执行层 |
| `_control` 的**下发段**（`link.position` / `link.stop` / IMU 调用） | 移入执行层 |
| `app_runtime._draw_preview` | 组帧 + `preview.render`，移入执行层 |

## 3. 唯一的难点：`_control` 怎么切

`_control` 现在同时做两件事：决定"该发什么"，以及"真的发出去"。硬拆会破坏时序与故障路径。

现成的边界是 `self.commands = {'yaw': None, 'pitch': None}`——它本来就是"决策结果"。

切法：

1. 逻辑层的 `_control` 只负责填 `commands` 与推进状态机（`aim.state`、`self_test`、`search`、`calibrator` 的推进），**不调用 link**。
2. 执行层新增 `apply_commands(link, commands, now)`，负责把非 `None` 的分量真正下发，并处理发送失败。
3. `process` 与 `idle` 在拿到决策结果后调用 `apply_commands`。

这样切开后：

- 逻辑层可以在 PC 上用假 link 单测，只断言 `commands` 的值；
- 执行层可以单独测"命令 → 串口帧"，不关心状态机；
- 故障路径仍由逻辑层判定，执行层只执行。

风险最高的一步，必须在改完后跑 `test_gimbal_aim` / `test_extension_control` / `test_main_self_test` 三组回归。

## 4. 目标文件结构

原则：**保留现有文件名，新增承载层**。理由是 `rectangle_center` 被 `aim_control`、`app_runtime`、
`target_api`、`vision/__init__` 与多个工具脚本 import，改名会牵动二十余处，收益不成比例。

```
vision/
  frame_poll.py     轮询层  to_gray / to_gray_frame / FramePoller
  rect_algo.py      算法层  blur / binarize / find_quads / select / 几何
  rect_output.py    执行层  draw_result
  aim_output.py     执行层  send_uart / apply_commands / stop_motion / notice
  rectangle_center.py  逻辑层（保留文件名）检测器 + 结果归因
  aim_control.py       逻辑层（保留文件名）VisionControl 状态机
```

过渡期允许旧文件 re-export 新模块的符号（如 `from .rect_algo import blur_frame`），
让现有 import 不破；四层稳定后删掉转发，统一改调用方。

## 5. 迁移顺序

每步都能独立验证，任一步失败可单独回滚：

1. **抽算法层**：新建 `rect_algo.py`，把六个纯函数搬过去；`rectangle_center` 改为 import。
   零风险，行为不变。
2. **抽执行层（绘制）**：新建 `rect_output.py` 放 `draw_result`，旧文件转发。
3. **抽轮询层**：新建 `frame_poll.py` 放 `to_gray` / `to_gray_frame`；把 `_capture_loop` 的
   读帧段包成 `FramePoller.poll()`，**先只搬函数，循环结构不动**。
4. **拆 `aim_control`**：按 §3 切 `_control`，新增 `aim_output.py`。这一步才真正改变调用链。
5. **清理**：删转发、同步 `tools/build_single.py` 的 `MODULES`、更新 `check_app` 清单与工具 import。

每步固定动作：提升 `BUILD_ID` → `build_single.py` → `check_pc.py`。

## 6. 风险与边界

| 风险 | 说明 | 应对 |
|---|---|---|
| 打包清单漏项 | 新增 `.py` 没加进 `MODULES`，单文件版会缺模块 | 每步都跑 `build_single --smoke`，它会列出嵌入的模块数 |
| 第 4 步时序回归 | `_control` 的下发顺序影响 ACK/E2 看门狗 | 只搬调用位置，不改顺序；三组控制类回归必须全绿 |
| 转发层长期残留 | re-export 会让"边界"变软，最后没人删 | 在窗口期内完成第 5 步，不把转发当常态 |
| 算法层被污染 | 图省事在算法函数里读 `cfg` 或写文件 | 算法层签名只收显式参数；配置由逻辑层取值后传入 |

**不做的事**：

- 不引入依赖注入容器、事件总线之类的框架。
- 不改线程模型（单识别线程 + 最新帧槽位）。
- 不改结果 dict 契约（`u/v/quad/reject/...` 的字段与语义）。
- 不重命名 `rectangle_center.py` / `aim_control.py`。
- 不为"层数好看"把 `state` 塞进算法层：逻辑层持有状态是允许的，算法层必须无状态。

## 7. 验收标准

分层完成后应满足四条，可逐条核对：

1. `rect_algo.py` 里没有任何 `import` 指向项目内其他模块（除 `numpy` / `cv2`）。
2. `rect_output.py` / `aim_output.py` 是唯一调用 `cv2.putText`、`uart.write`、`link.position` 的地方。
3. 删掉 `rect_output.py` 后，逻辑层与算法层仍能 import 并通过单测。
4. 用假 link 跑一遍完整决策链，`commands` 与拆分前逐帧一致。
