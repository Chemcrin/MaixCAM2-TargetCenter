# 视觉识别问题分析（MaixVision 实拍录像）

> 对象：`maixcam2_rect_center/` 识别链路（`vision/rectangle_center.py` 及其搜索/几何依赖）。
> 云台部分（`gimbal_*` / `aim_control` / `stepper_link`）本轮**只读不改**。
> 输入：`vest视频/maixvision.mp4`（MaixVision 预览面板的桌面录屏，29.995fps，1022 帧，约 34s）。
> 结论口径：本文件是**阶段性快照**，数值与结论只对这份录像与该提交成立。

---

## 1 结论摘要

1. **识别链路没有"崩"，是"少一条边就整帧丢"的硬门在实拍场景里频繁触发。** 失败帧中约 80%
   死在窄带精修——四条边凑不出 3 条可实测边；这些帧的物理事实是手、画面边缘或过曝把胶带挡掉了。
2. **真正能修的是搜索层与验证层的口径冲突，已修。** 提案阶段禁止四边形出画，而验证阶段
   明确支持"最多 1 条边被画面裁掉"——贴边/大靶的候选在搜索层就被丢掉，验证层的容忍从未被用到。
   修掉这一条，同一份录像的有效率 **20.6% → 32.1%**，最长连续失锁 **211 帧 → 87 帧**。
3. **此前记录的 26% 有效率本身是被测试工具污染的。** 旧的 `--pane maixvision` 裁切把 MaixVision
   的"直方图/LAB"工具条一起裁进画面（占裁切高度约 36%），底部黑带既稀释了靶纸分辨率，又会
   伪造下边缘的暗带证据。按真实面板重裁后，同一份代码的有效率是 20.6%，不是 26%。

## 2 测试方法（可复现）

```bash
# 回放 + 出标注视频 / 逐帧 json / 拼图 / 汇总
"D:/Python311/python.exe" -B tools/run_video.py --video "../vest视频/maixvision.mp4"

# 失败归因 + 尸检（哪一层拒的、四边覆盖率多少）
"D:/Python311/python.exe" -B tools/diagnose_video.py --video "../vest视频/maixvision.mp4"

# 参数敏感性扫描（不改文件，只覆盖本次进程的 Config）
"D:/Python311/python.exe" -B tools/run_video.py --video "../vest视频/maixvision.mp4" \
    --no-video --quiet --set MIN_EDGE_COVERAGE=0.45
```

指标定义：**有效率** = 有效帧 / 处理帧；**partial** = 有效帧中"3 条实测边 + 1 条先验边"的比例；
**最长失锁** = 连续无效帧的最大长度（比平均值更能反映"云台会不会开始乱找"）。

裁切与分辨率：MaixVision 图像面板在 2560×1440 录屏里位于 `x∈[2058,2519]`、`y∈[280,496]`，
即 461×216。`--size 640x0` 按该比例推算为 640×300，**不再纵向拉伸**。旧的 `--pane maixvision_ui`
保留下来只用于对照历史数字。

## 4 失败归因（数据，不是推测）

### 4.1 按层次

对每个失败帧做尸检：拿上一帧的锁定框重跑一次窄带精修，再跑一次带 `diagnostic` 的验证，
定位它死在哪一步。

| 归因 | 修复前 | 修复后 |
|---|---|---|
| `track_refine`（精修凑不出 3 条实测边） | 679（89.8%） | 549（79.1%） |
| `track_coverage`（精修出框但覆盖率不足） | 35（4.6%） | 101（14.6%） |
| `cold_no_proposal`（无锁定且搜索层零提案） | 33（4.4%） | 33（4.8%） |
| 出画/退化/U 形等其它 | 9（1.2%） | 11（1.5%） |

### 4.2 按边（为什么精修会失败）

精修对每条边统计"找到可用跳变的采样列数"（满值 24）。修复前 552 个 `track_refine` 失败帧的分布：

| 可测边数 | 0 | 1 | 2 | 3 | 4 |
|---|---|---|---|---|---|
| 帧数 | 11 | 146 | 195 | 136 | 64 |

- **只有 2 条边可测的 195 帧**是最大的一类：几何上无法定出中心，判死是对的。
- **3~4 条边可测却仍判死的 200 帧**才是真正的可疑区间：边找到了，但撞在
  "内点不足 `MIN_LINE_COVERAGE`"或"拟合残差超 `MAX_LINE_RESIDUAL_PX`"上。
  这类帧最值得继续挖，但**不能靠放宽残差门限来修**——它是 0.49px 精度的来源。

### 4.3 阈值不是瓶颈

对 8 个判据各放宽一档，同一条录像：

| 变体 | 有效帧 | 最长失锁 |
|---|---|---|
| 基线 | 210 | 211 |
| `MIN_EDGE_COVERAGE` 0.55→0.45 | 219 | 211 |
| `MAX_LINE_RESIDUAL_PX` 0.8→1.2 | 222 | 211 |
| `TRACK_RADIUS` 12→16 | 231 | 211 |
| `WEAK_EDGE_COVERAGE` 0.25→0.18 | 211 | 211 |
| `MIN_LINE_COVERAGE` 0.55→0.45 | 210 | 211 |
| `MIN_EDGE_CONTRAST` 20→14 | 238 | 211 |
| `MAX_DARK_BRIGHT_RATIO` 0.72→0.80 | 222 | 211 |

全部只挪动 1~3 个百分点，**最长失锁一动不动**。结论：这段录像的损失是"目标看不见"，
不是"判据太严"；继续拧阈值属于过拟合测试集。

## 5 冲突的代码逻辑（按影响排序）

### C1 搜索层禁止出画，验证层允许出画（已修，+11.5pt）

`ContourLocator._quads_from_mask` 用 `quad_is_valid(..., allow_clipped=False)` 默认值体检候选，
任何越界即丢；而 `_verify` 自己用 `allow_clipped=True`，并靠 `MAX_CLIPPED_EDGES` 明确支持
"最多 1 条边被画面裁掉"。结果是**验证层的能力被上游提前剥夺**：靶纸贴边或占满画面时，
外框候选根本进不了 `_search`，只能退回全图重搜——而重搜还是同一套提案规则。

实拍证据：t≈9s 的帧上 12 个提案全部是靶纸内部的同心圆（外框轮廓因与背景连通、
四角越界被判"四边形无效"），外框一次都没被提出，于是整帧 `no_black_frame`。

修法：提案阶段也按 `allow_clipped=True` 体检，由 `SEARCH_ALLOW_CLIPPED` 控制（默认开）。
验证层不动——误检仍由暗带证据挡。副作用是搜索路径的候选变多，PC 上检出中位耗时 5.7→8.3ms。

### C2 失败一律记 `no_black_frame`，阶段信息丢失

`process()` 的失败分支原本不区分"追踪失败""ROI 重搜失败""全图重搜失败"，统一写
`stage='no_black_frame'`，8.9 成的帧被同一个标签吞掉。

**已修**（保持 `stage` 语义不变，只增字段）：失败帧额外带 `fail_stage`（本帧走过的层级，如
`track+full`）与 `fail_reason`（**首次**失败原因：`track_refine` / `track_verify` /
`roi_no_proposal` / `roi_rejected` / `no_proposal` / `rejected`）。`[perf]` 行尾追加
`det_fail=<fail_stage>/<fail_reason> det_props=<提案数>`；`run_video` 汇总里出层级与原因分布；
标注视频的 "NO LOCK" 也带上这一对码。

同一份录像的实测分布：`track_refine` 548、`track_verify` 113、`rejected` 33
（另 `no_proposal` 在冷启动帧上零星出现）。与独立尸检脚本的结论一致，说明标签口径可信。

### C3 `PARTIAL_MIN_EDGES=3` 与验证门叠加，实际要求"3 条实测且强"

`_refine(require_all=False)` 允许 3 条实测 + 1 条先验边；但 `_verify` 仍要求
"≥3 条边 `coverage ≥ MIN_EDGE_COVERAGE`"，而弱边（手挡半条、内点刚好够 5 个）覆盖率通常在 0.3~0.5。
于是"3 条实测"里只要有一条是弱边，整帧判死。修复后有 101 帧落在这一档（其中 33 帧只差一条边）。
口径建议：弱边要么计入"实测"并降低该边的覆盖率要求，要么明确不计入"实测"——
现在的写法是同一件事在两个函数里各判一次，结论不一致。

### C4 `config.py` 里 6 个参数写了不生效

`apply_aim_profile` 在文件末尾按档位覆盖 `GAIN_YAW/PITCH`、`GAIN_COARSE`、`RPM_FINE/COARSE`、
`MAX_STEP_PULSES`。字面值 `GAIN_YAW = 0.5`，`AIM_PROFILE="smooth"` 下实跑 0.30。
现场照着字面值调参必然调错。本轮已在注释里逐个标注"被 profile 覆盖"，机制本身没动
（用户明确要求保持 `smooth`）——真正的解是把这 6 项从字面定义里删掉、只留 profiles 表。

### C5 搜索路径最多做 4 次全边精修

`_search` 对"四边完整"的候选先 `_finalize(require_all=True)`，失败再来一次 `require_all=False`；
而 `_finalize` 内部本来就有同样的回退。两次调用的差别只剩"精修成功但验证失败"这一支，
代价是搜索帧的最坏耗时翻倍。属于性能问题，不是正确性问题。

### C6 失锁后 `_track` 永不清空，复锁门用陈旧面积比

`process()` 失败时清 `_smooth/_prev_quad/kalman`，但保留 `_track`；`_reacquire_consistent`
拿它做面积比门（`REACQUIRE_AREA_RATIO=3`）。长时间丢失后目标距离变化（变焦/走近），
面积比一超 3 就被拒——这正是"明明看见了却不锁"的另一条路径。建议加时效：`_lost` 超过
N 帧后跳过面积门（位置门本来就没设，尺度门只在短时间内有意义）。

| 改动 | 性质 | 效果 |
|---|---|---|
| `SEARCH_ALLOW_CLIPPED`：提案阶段与验证层同口径 | 行为 | 有效 210→328（+11.5pt），最长失锁 211→87 |
| `--pane maixvision` 重裁到真实面板 461×216，默认按比例出图 | 测试工具 | 旧数字 26% 被证伪，基线回到 20.6% |

| 7 处工具默认输出统一改到 `reports/`；`check_app` 增 C11 | 工程 | 项目目录 59MB→1.5MB，回到 MaixVision 30MB 上限内 |

——说明新增的锁定是**贴着画面边缘的大靶**，不是角落杂物被误当成靶。

## 7 未采纳的方案及理由

**"2 条实测边 + 2 条先验边"的降级追踪**：能把约 35% 的失败帧变成 partial 锁定，但实测不成立。
统计 34 段"只有 2 条边可测"的连续区间，区间两端（前后最近一次 3 边以上锁定）的中心位移
中位 66px、p90 113px。先验边停留几十像素之外，据此算出的中心会持续偏几十像素，
对闭环是比"丢失"更坏的状态。**维持"≥3 条边"硬门。**

**放宽 `MAX_LINE_RESIDUAL_PX` / `MIN_EDGE_COVERAGE`**：见 §4.3，收益 1~3pt 且要拿精度换。

**提高 `SEARCH_WIDTH`**（320→480）：能改善搜索层对小靶的提案率，但搜索耗时约平方增长；
本轮优先保证 30fps，未验证，列为待测。

## 8 建议的下一步（按性价比）

1. ~~`fail_stage` 落进 `result` 与 `[perf]` 日志~~（已完成）：下一步是拿板端真实分布，
   看 `track_refine` 与 `track_verify` 各占多少——前者要改精修的内点/残差判据，
   后者要改暗带证据判据，方向完全相反，必须先分清。
2. **板上实测搜索耗时**：本轮 PC 上中位 8.3ms 不能外推到板端（历史板端全图搜索 39~71ms）。
   上板看 `[perf] det_ms / det_stage`，确认 30fps 是否还成立。
3. **C3 的口径统一**：弱边只在一处判。建议 `_verify` 接受 `weak_edges` 显式传入，
   对弱边把覆盖率要求降到 `WEAK_EDGE_COVERAGE`，不再整帧判死。
4. **C6 的时效门**：`_lost` > N 帧后跳过面积比门，避免"看见了不锁"。
5. **验收集分层**：这段录像是手持演示（手挡、出画、镜头扫到别处），不能当精度验收。
   精度用合成集（现有 76+121 例）；跟踪鲁棒性另拍一段"165cm 静靶 + 云台小角度摆动"的录像，
   两者分开看指标。
