# 板端故障排查 · 2026-10-18（v0.9.0 → v0.9.1）

现场两个症状：① 锁丢失后无法快速复锁；② 云台完全不动。
结论：它们是**两条独立的故障链**，都已定位到代码并修复；其中 ② 是致命 bug。

## 1. 【致命】ACK 看门狗按"全局"武装，一个静默轴拖死整机

`vision/stepper_link.py` 原判据：

```python
if timeout_ms > 0 and self._stats["ok"] > 0:   # ← 全局计数
    for axis in self._ports:
        ...
        if self._timeout_count[axis] > RX_TIMEOUT_LIMIT:
            out["reason"] = "ack_timeout:%s" % axis   # ← 整链路 FAULT
```

`_stats["ok"]` 是**两条轴共用**的计数。只要 yaw 的驱动器回了确认帧，看门狗就
对本轴和 **pitch 一起**武装；而 pitch 的驱动器如果 `Response=None`（出厂默认，
不主动回帧），就永远收不到确认帧 → 每 300ms 记一次超时 → 20 次后
`FAULT: link:ack_timeout:pitch`。

这与 `config.py` 里的注释承诺**正好相反**：

> 只有在收到过确认帧（驱动器 Response=Receive/Reached/Both）之后才启用；
> Response=None 时收不到确认帧，该判据自动不生效，不会误判 FAULT。

**复现**（PC 上可跑，`yaw` 回帧、`pitch` 静默）：

| 版本 | 结果 |
|---|---|
| v0.9.0 | `FAULT: link:ack_timeout:pitch`，第 5 条指令后两轴全部停发 |
| v0.9.1 | `COARSE`，连续 40 帧两轴各发 40 条指令 |

### 修法

- 看门狗改为**按轴武装**：新增 `_ack_seen`，该轴**自己**回过帧才要求它继续回帧。
- 从未回过帧的轴：只打印一次可执行的告警，**停用该轴的 ACK 判据**，不判障：
  ```
  [gimbal] WARN pitch 从未返回确认帧：驱动器 Response 可能不是 Receive/Reached/Both；
  该轴 ACK 看门狗已停用（不影响发令，但无法确认到位）
  ```
- 保留真正该判障的两条：**回过帧之后又断链**（`ack_timeout`）与 **E2 洪水**。
- 新增回归 `test_gimbal_aim.py::test_silent_axis_still_moves`（12 项全过）。

> 取舍说明：驱动器不回帧时，我们无法区分"Response 关了"和"驱动器死了"。
> 但运动是**相对、限幅、带发散守卫**的（`MAX_STEP_PULSES` / `COMMAND_INTERVAL_S` /
> `DIVERGE_GUARD`），让一个静默轴拖死整机是更坏的失败模式。
> 若想恢复严格确认，把驱动器菜单 `Response` 设为 `Receive` 即可，判据会自动重新生效。

## 2. 【复锁慢】精修把整条边的采样一刀切判越界

`vision/rectangle_center.py::_refine` 原判据：

```python
inside = ((points[...,0] >= 1) & ... ).all(axis=2)   # ← 任一探测点越界，整条 t 采样作废
good_edges = inside & (strength >= ...)
```

半径 `TRACK_RADIUS=12` 时，每条边沿法向采样 25 个点（±12px）。**大靶或靶贴边**
时（顶边 y≈10 很常见），最外侧的探测点伸出图像 → `.all()` 把该边 24 个采样点
全部判为无效 → `refitted < 4` → `_refine` 返回 `None` → 本帧 `track` 失败 →
退化到 `roi_search` / `full_search`。

**复现**（靶心 (430,180)，顶边 y≈10.3）：

| 半径 | v0.9.0 | v0.9.1 |
|---|---|---|
| r=6 | ok | ok |
| r=12（跟踪用） | **None** | ok |
| r=20（救援用） | **None** | ok |

丢锁 → 复锁的整段序列（同一张图，4 帧空白后重新出现）：

| 版本 | 复锁后逐帧 stage |
|---|---|
| v0.9.0 | `full_search → roi_search → roi_search → roi_search …`（每帧 3~8ms，板端 0.3~1.4s） |
| v0.9.1 | `full_search → **track → track → track …**`（0.8ms，板端 ~57ms） |

这解释了"锁上了也留不住"的观感：**不是没找到，是找到了下一帧又掉回搜索**，
而每一次搜索在板端要 0.3~1.4s，结果全部过期，云台自然也没法动。

### 修法

逐探测点判越界，只用"中心差分两个抽头都在图内"的列参与峰值挑选；邻点越界时令其
等于峰值（曲率必为负 → 修正量 0，退回整数偏移），既不用边界复制出来的假值插值，
也不因此丢掉整条采样。

精度复核：`verify_subpixel.py` 121 个相位 **121/121、最大 0.0852px**，与修复前
逐位相同；全套门禁 24/24。

## 3. 仍然存在、但本轮不改的两件事

1. **板端单帧耗时**：`track det_ms=56~115ms`（PC 0.81ms），`full_search 0.3~1.4s`。
   锁定态 ≈9~17fps，达不到 30fps。占比上 PC 是"精修 61% / 验证 37%"，板端需用
   `tools/profile_frame.py` 实测确认。可动的旋钮：`SEARCH_WIDTH`(320) /
   `SEARCH_MAX_CONTOURS`(16) / `TRACK_RADIUS`(12) / `EDGE_SAMPLES`(24)。
   **不要**为了速度关 `SEARCH_EXHAUSTIVE`。
2. **主线程绘制成本**：`draw=20~40ms/帧`（PC ~2ms），已把 `capture` 压到 20~30fps。
   它不阻塞识别线程（识别在独立线程），但会与识别抢 CPU。可选：`SHOW_WIDTH=480`。

## 4. 重新上板后的验收判据

烧 `dist/main_single.py`（BUILD_ID `2026-10-18-relock-ackfix-v0.9.1`）后，日志里应当看到：

```
[rect-center] 2026-10-18-relock-ackfix-v0.9.1 search_width=320 ...
[gimbal] WARN pitch 从未返回确认帧 ...   ← 预期出现一次；若两轴都回帧则不出现
```

并且：

| 观察项 | 通过标准 |
|---|---|
| `[aim] state` | 出现 `FINE` / `SETTLE`，**不再**出现 `FAULT: link:ack_timeout:*` |
| `[aim] yaw=/pitch=` | 至少一轴变成 `CCW/nnnp` / `CW/nnnp`（不再是 `-`） |
| `det_stage` | 稳态长期 `track`（`masks=0`），不再长期 `roi_search/full_search` |
| `detect_fps` | 锁定态尽量高；若仍 <30，跑 `tools/profile_frame.py` 看占比 |
| `[aim] dx/dy` | 随云台动作**收敛**；若持续变大 → 改对应 `DIR_SIGN_*`（只改符号，别动 `PULSE_PER_PX`） |

若 `state` 仍是 `FAULT`，日志会直接给出原因：
`link:*`（串口/驱动器）、`tx:*`（写失败）、`diverge:*`（方向反）、`self-test:*`。

## 5. 2026-10-18 板上实测结果（v0.9.1，MaixCAM2 / 2×1.2GHz）

用 SSH 部署到 `/tmp/maixpy_run` 后实跑（相机对准靶纸）：

| 观测 | 结果 |
|---|---|
| `BUILD_ID` | `2026-10-18-relock-ackfix-v0.9.1` ✅ |
| `FAULT` 次数 | **0**（旧版开机数秒内必现 `ack_timeout:pitch`） |
| `WARN` | 仅 1 条，`pitch 从未返回确认帧` ✅ |
| 发令 | `[aim] state=FINE dx=1.88 dy=-1.01 yaw=CW/2p pit=CCW/1p` → **两轴都动** ✅ |
| 收敛 | 连续帧 `dx: 1.88 → 1.70 → 1.34 → -0.95`，`state` 进 `SETTLE` ✅ |
| 锁定态单帧 | `det_ms=39~71ms`（全应用同跑，含 draw 36~43ms）；**纯检测器空载 17.3ms** |
| 搜索态单帧 | 全图搜索 0.5~1.4s，`locate`(=Canny+轮廓) 占 **100%** |

**关键结论**
- 两条故障链都已闭环：不再 FAULT，双轴能发令，误差收敛。
- 检测器本身 17.3ms/帧（≈58fps）；**实际应用里被主线程 draw（36~43ms/帧）抢走 CPU**，
  掉到 39~71ms（14~25fps）。要冲 30fps，下一步应削 draw，而不是动检测参数。
- `locate` 是搜索态的唯一瓶颈，`_verify` 不是 —— 所以"给候选验证减半"没有意义，
  真要提速只能降 `SEARCH_WIDTH` / `SEARCH_MAX_CONTOURS`。

> ⚠ **停止应用只能用 MaixVision 的停止按钮，不要 `kill` / `pkill`。**
> 实测两次（`pkill -f main.py`、`kill -INT <pid>`）都在数秒内导致**整机重启**
> （相机/ISP 流未拆干净）。重启还会清空 `/tmp/maixpy_run`，看起来像"部署丢了"。

## 6. 复锁与云台：当前实现状态（2026-10-18 复核）

### 6.1 丢失后复锁 —— 已实现，代价是**恰好 1 个搜索帧**

`process()` 的路径（`vision/rectangle_center.py`）：

```
有 _track → ① 用上一帧四角(+运动外推)做窄带精修  → track
         ② 失败且 _roi_retry → ROI 搜索           → roi_search
         ③ 仍失败 → 全图搜索（同帧，绝不用 elif）  → full_search
```

`_roi_retry` 用一次即置 False、成功才恢复 —— 所以"丢锁后连续多帧"只会做 1 次 ROI，
不会反复局部搜。逐场景实测（PC，解析真值，目标全程在画面内）：

| 场景 | 搜索帧 | 首帧误差 | 之后 |
|---|---|---|---|
| 原位遮挡 1 帧 | **0** | 0.004px | 全 `track` |
| 平移 100 / 180px | **1** | 0.004px | 全 `track` |
| 平移 180px + 下移 60px | **1** | 0.004px | 全 `track` |
| 平移 120px + 缩小到 140px | **1** | 0.009px | 全 `track` |
| 平移 120px + 放大到 300px | **1** | 0.018px | 全 `track` |
| 平移 150px + 旧位置有干扰框 | **1** | 0.004px | 全 `track`（未误锁干扰框） |
| 丢失 20 帧后平移 150px | **1** | 0.004px | 全 `track` |

**关键改进**：修复前（`inside.all()` 的 bug）复锁后**每一帧**都会退回 `roi_search`
（板上 0.3~0.4s/帧），看起来"锁上了又丢"；现在只有**第一帧**付搜索代价，第二帧起
就是 17.3ms 的窄带跟踪。

换算到板上：复锁时延 ≈ **1 个全图搜索帧**。该帧耗时取决于画面杂波——板端实测
全图搜索 0.53~1.41s 属"有候选但全部不通过"的最坏情形；干净靶应在 0.1~0.2s 量级
（未单独实测，用 `detect_black_frame` 打点即可）。

### 6.2 云台操控 —— 发令链路已修好，方向"yaw 已实证 / pitch 待实证"

**（a）发令链路**：`FAULT: link:ack_timeout:pitch` 修复后，板上日志实测
`[aim] state=FINE dx=1.88 dy=-1.01 yaw=CW/2p pit=CCW/1p` —— **两轴都在发脉冲**，
且 `dx` 连续收敛 `1.88 → 1.70 → 1.34 → -0.95`（过零），这是 yaw 方向正确的直接证据。

**（b）符号推导（两轴自洽）**：相机与激光同装云台 ⇒ 云台转过去时靶心在画面里反向移动。

| 轴 | CCW 物理方向 | 若执行 CCW，图像里靶心 | 要减小正误差（靶心偏右/偏下）应执行 | 代码 `ccw = e*sign>0`，sign=-1 |
|---|---|---|---|---|
| yaw | 左 | 向右移（u↑） | CW（右） | e>0 → ccw=False → **CW** ✓ |
| pitch | 上（仰） | 向下移（v↑） | CW（下） | e>0 → ccw=False → **CW** ✓ |

两轴符号与 `AGENTS.md §2` 的实测轴映射自洽，不是随手填的。

**（c）比例鲁棒性**：闭环对 `PULSE_PER_PX` 误差 0.25×~6× 都能 SETTLE（25~235 帧），
所以 3.67 是占位值**不致命**；只有 `DIR_SIGN_*` 必须对。

**（d）仍未被实证的部分**（诚实标注）：

1. **pitch 方向**只有弱证据：板上 `dy` 序列 `-1.01 → -2.47 → -2.60 → -2.16`，
   幅值只有 1~3 脉冲（≈0.3~0.8px），与机械回差/纸面抖动同量级，不能定性。
   需要一个 **>20px 的大误差**才能判定（把靶纸放到画面偏上/偏下 20px 以上看 dy 是否收敛）。
2. **pitch 从不回 ACK**（`Response` 未开）：能发令、能动，但**无法确认到位**，
   `AIM_WAIT_MOTION` 的时间估算就是唯一依据。要闭环质量更好，把驱动器菜单
   `Response` 设为 `Receive` 即自动恢复确认。
3. **`PULSE_PER_PX` 未标定**：影响收敛速度与超调量，不影响方向；建议按
   `开环标定` 跑一次填回。

### 6.3 一句话状态

> 复锁：**已完成并量化**（1 帧搜索）。云台：**能发令、yaw 方向已实证收敛**；
> pitch 方向与到位确认**尚未实证**，需一次大误差测试 + 打开驱动器 `Response`。

### 6.4 自检序列（`SELF_TEST_PULSES>0` 的默认口径）实际是 **6 段**，先 yaw 后 pitch

| 段 | 轴 | 方向 | 脉冲 | 说明 |
|---|---|---|---|---|
| 1/6 | yaw | **左**（CCW） | 400 | 出去 |
| 2/6 | yaw | **右**（CW） | 800 | 跨过中位到另一侧 |
| 3/6 | yaw | **左**（CCW） | 400 | 回中 |
| 4/6 | pitch | **上**（CCW） | 400 | 出去 |
| 5/6 | pitch | **下**（CW） | 800 | 跨过中位到另一侧 |
| 6/6 | pitch | **上**（CCW） | 400 | 回中 |

- 轴序：**先左右、后上下** ✅，但每轴是"出去→反向两倍→回中"三段，全程约 **5.6s**
  （每段运动 0.5~0.7s + `SELF_TEST_SETTLE_S=0.35`）。
- 幅度：400 脉冲 ÷ 3200 脉冲/圈 = **电机轴 45°**（有减速比时输出轴更小），中间段 800p = 90° 行程。
  ⚠ `vision/gimbal_self_test.py` 的模块 docstring 仍写"yaw ±15°，pitch ±30°" —— 那是**角度模式**
  （`SELF_TEST_PULSES=0`）的口径，固定脉冲模式不适用；已知文档缺口，下次改 `vision/*` 时一并修正
  （本轮为一句注释单独升 BUILD_ID 不划算，故意未改）。
