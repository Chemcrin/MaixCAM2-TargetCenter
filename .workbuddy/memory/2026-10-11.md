**版本核对（结论）**：

  **用户确认：不使用该 zip，直接跑 `maixcam2_rect_center/` 目录下的文件** → 故**版本无问题**，zip 只是历史遗留产物（不必重建）。

**2fps 根因（代码侧）**：`SyncPreview`（`SHOW_ASYNC=False`，主进程内 `Display.show`）是**同步阻塞**调用。
`_next = now + max(0, _period − show_s)`：
- 若 `show_s < _period(=1/SHOW_SLOW_MIN_FPS=0.5s)` → 每帧后有 idle，主循环得以脱身；
- 若 `show_s ≥ 0.5s` → `max(0,…)=0` → **每个 iteration 都 show 且每次阻塞 ~0.5s** → 主循环与显示**同时**塌到 ≈2fps。
且 `main.py` 的 `fps` 口径 `dt = after_show − last` **把 show 耗时算进主循环**，故 `[perf] FPS=` 也会≈2。
**判别**：屏幕 `FPS <disp> loop <loop>`；若 `loop` 也≈2 → 主循环被图传拖累；若 `loop` 高（20~30）→ 仅显示受限。

**关键事实**：v0.3.2 **未改动显示/预览路径**（只改了追踪手感）。帧率治理(v17/v20)本就在基座里，且其目标是
"诚实计量 + 慢帧不塌到 0.4fps"，**并不提升显示帧率**；`SHOW_SLOW_MIN_FPS=2.0` 正是"慢图传时恰好停在 2fps"的来源。

**可选对策**（待在用户确认后实施）：① 重建 zip 为 v0.3.2；② 降 `SHOW_WIDTH` 320→160 减小图传量；
③ 正式追踪 `SHOW=False`（循环完全不受显示影响）；④ 预览自动降级/停用（图传长期慢时自保）。
