**版本核对（结论）**：

  **用户确认：不使用该 zip，直接跑 `maixcam2_rect_center/` 目录下的文件** → 故**版本无问题**，zip 只是历史遗留产物（不必重建）。

**2fps 根因（代码侧）**：`SyncPreview`（`SHOW_ASYNC=False`，主进程内 `Display.show`）是**同步阻塞**调用。
`_next = now + max(0, _period − show_s)`：
- 若 `show_s < _period(=1/SHOW_SLOW_MIN_FPS=0.5s)` → 每帧后有 idle，主循环得以脱身；
- 若 `show_s ≥ 0.5s` → `max(0,…)=0` → **每个 iteration 都 show 且每次阻塞 ~0.5s** → 主循环与显示**同时**塌到 ≈2fps。
且 `main.py` 的 `fps` 口径 `dt = after_show − last` **把 show 耗时算进主循环**，故 `[perf] FPS=` 也会≈2。
**判别**：屏幕 `FPS <disp> loop <loop>`；若 `loop` 也≈2 → 主循环被图传拖累；若 `loop` 高（20~30）→ 仅显示受限。

**关键事实**：v0.3.2 **未改动显示/预览路径**（只改了追踪手感）。帧率治理(v17/v20)本就在基座里，且其目标是
"诚实计量 + 慢帧不塌到 0.4fps"，**并不提升显示帧率**；`SHOW_SLOW_MIN_FPS=2.0` 正是"慢图传时恰好停在 2fps"的来源。

**可选对策**（待在用户确认后实施）：① 重建 zip 为 v0.3.2；② 降 `SHOW_WIDTH` 320→160 减小图传量；
③ 正式追踪 `SHOW=False`（循环完全不受显示影响）；④ 预览自动降级/停用（图传长期慢时自保）。

## 根因实锤：MaixVision 服务连接 timeout → `Display.show` 每帧阻塞 ~505ms（01:0x）

用户贴出 v20 的完整运行日志，**决定性三行**：
```
[error] handle_connect error: Timer Expired
-- [E] connect maixvision service timeout
Error getting remote endpoint: asio.system:9 (Bad file descriptor)
```
即 **MaixVision 服务链路没建立起来**（用户也观察到"上位机不显示画面"）。
同步测量：`show` 每帧稳定 **503~511ms**（≈ 代码注释里写的"网络超时可能阻塞 500ms"，`SHOW_SLOW_MS=80` 只是判慢阈值）。

**相机侧结论（排除相机）**：`read=0.5~0.9ms`，`[perf-max] read=0.6~1.7ms` —— 取帧几乎瞬时；
`frames=4/窗口(~2s)`、`loop≈510~546ms`、其中 `show≈506ms` ⇒ **主循环 96% 时间卡在 show 上，1.9fps 由它决定**。
（注：read 极快也意味着它多半"取最新帧"、不反映相机真实采集率 —— 故仍需 `probe_camera_fps.py` 的 A 段作最终证据。）

**修正后的根因表述**：不是相机、不是识别、不是版本；是 **`display.Display().show()` 在 MaixVision host 链路不可用时每帧阻塞到超时(~500ms)**。
**两条解法**：① `SHOW=False` 彻底不调 show（主循环回 ~60fps，v20 代码自己就这么建议）；
② 修复 host 链路（重连/重启 MaixVision、换线、重启设备）后再测。**`SHOW_ASYNC=True` 仍不可用（v18 证伪）。**
本次日志同时确认 v20 参数已生效（`死区=3.0 限幅=80 低通0.10 限速400 acc=160 等待运动=True`）。
