> 板端 BUILD_ID：`2026-10-13-wide-refine-recovery-v0.6.5`（C 轨 v0.6.5，与本地
> `maixcam2_opus_rework_Acp/main.py` 一致）。
> 本文档目的：把"现在识别的问题"整理成可执行的修改清单，供接下来改代码使用。

## 0. 结论速览（TL;DR）

**靶纸在画面里清晰可见，但识别吞吐只有 3.2 fps（单帧约 312 ms），超过 200 ms 新鲜度门槛，
全部结果被判 `stale`，闭环一直停在 HOLD，云台收不到任何有效测量。**

这不是"识别不到靶纸"，而是**"识别太慢 → 结果全部过期 → 闭环被锁死"的系统性卡死**，
并伴随 CPU 争抢连带拖慢主循环与显示。次要异常：`[aim]` 日志出现本地源码**不可能产生**的
dx 巨值，提示**板端烧录的构建可能与本地源码不一致**——这是改代码前必须第一步排除的问题。

### 读数口径（避免误读，源码依据）

- `capture=` / `disp=` / `low1=` / `detect_fps=` **都是 fps 不是 ms**（`telemetry.format_perf_line`）；
  `low1` 是**显示侧** FrameRate 的"最慢 1% 帧间隔倒数"（`rate_meter.FrameRate`），不属于识别线程。
- `read/draw/loop` 属**主循环**；`show` 属**显示线程**（`app_runtime._capture_loop`）。
- `stage=stale` 是**显示层**的过期占位（`preview.display_result`：age > RESULT_MAX_AGE_S 时
  整体替换为 `{valid:False, stage:"stale"}`）——**它掩盖了检测器自己的 stage**（见 P1-2）。
- `[aim]` 行由主线程每 2s 打印 `GimbalAim.status_line()`，dx/dy 取自最近一次 `_emit`。
- `drop(vision)` 每秒增长约 26~27（32017→32069→32119，间隔 2s）≈ 主循环提交速率(≈29fps)
  − 识别完成速率(3.2fps)，与"识别跟不上、最新帧覆盖旧帧"的 worker 模型吻合。

## 4. 问题清单（按严重度排序）

### P0-1 识别吞吐塌方：detect_fps=3.2，单帧 ~312ms

**证据**：`detect_fps=3.2/3.1`；`drop(vision)` 每秒 +26；`age` 165~613ms。
**机理**（源码链）：检测器三级级联 `track → roi_search(仅一次) → full_search`
（`rectangle_center.process`）。`full_search` = `_search(g)` 全图：先缩到 320 宽，
再对 [上次阈值] + Otsu + 8 档 `DARK_THRESHOLDS`（按 6 去重，约 9~10 档）逐档
`threshold + morphologyEx(CLOSE) + _candidate_quads`；**每个候选**都要
`_verify`（四边各 24 点采样），失败且 `REFINE_RADIUS_WIDE=20 > REFINE_RADIUS=6` 时再
`_refine(wide) + _verify + RECOVER_* 确证门槛`；成功还要 `_refine(6) + _verify`。
`SEARCH_EXHAUSTIVE=True` 时候选数不截断（cap=None），最后还有 Canny 兜底。
最坏单帧 ≈ 10 档 × 8 候选 × 3~4 次全分辨率(640×480)边缘采样 + Canny。
PC 上约 10ms，板端约 300ms（约 30 倍，符合该算力平台的单线程 Python+OpenCV 预期）。
**待确认**：track 为何不生效——是 `full_search` 从未成功（`_track` 为 None），
还是成功了但下一帧 track 的 `_refine(12px)+_verify` 过不了、又掉回
roi_search+full_search？当前日志看不到检测器真实 stage（见 P1-2），两种成因修法不同。

### P0-2 结果全部过期：`valid=false stage=stale`，闭环被锁死

**证据**：连续多条 `[perf]` 全部 `valid=false stage=stale`；`age` 165/613/504ms。
**机理**：`RESULT_MAX_AGE_S=0.20`。识别 312ms > 200ms ⇒ 检测即使成功，到
`accept_result`（aim_control.py:87-98）和 `display_result`（preview.py:33-34）时都已过期，
被双层替换为 `stage="stale"`。`_control` 收到无效结果 → `GimbalAim._on_lost` →
HOLD、`lost++`，一条闭环指令都不发。
**这正是 `tools/test_real_scene.py:43` 注释预警过的风险**（"板端 detect_fps=3.1、
结果 age>200ms 全被判 stale"）——已实际发生。
**旁证**：`[aim] lost` 序列 0→2→1，说明**偶尔有帧 <200ms 赶上了新鲜度**（SETTLE 出现过），
系统处于"勉强够到门槛"的临界状态，不是全黑。

### P0-3 靶纸清晰可见却锁不上：v0.6.5 宽半径修复未在板端见效

**背景**（`tools/test_real_scene.py:40-44` 注释，2026-10-13 实机定位的真因）：掩膜候选
四边形比胶带外沿**低约 14px**，`_verify` 只从边向里采 2~6px ⇒ 采到纸面当"暗带"误拒；
窄半径精修（6/12px）纠不动 ⇒ 画面里黑框清清楚楚却永远 `no_black_frame`。
**修复**（v0.6.5）：`_verify` 失败时先用 `REFINE_RADIUS_WIDE=20` 精修把四边拉回真边再验，
外加 `RECOVER_MIN_CONTRAST=80` / `RECOVER_MAX_DARK=100` 确证门槛；PC 固件
`real_board_frame.png`（板端真实帧）回归通过。
**现状**：板端仍是 3.2fps + 全 stale，与修复前（3.1fps + 全 stale）几乎无差别。
两种可能：(a) 板端烧录的构建不含该修复（BUILD_ID 未随代码刷新而更新，违反烧录纪律）；
(b) 修复在实机动态条件（光照/运动/320 宽降采样）下不够。**先查 (a) 再改算法**。
辅证：P1-1 的 dx 巨值在本地源码（含 dist 单文件版）上**不可能产生**。

### P1-1 `[aim]` 日志 dx=3620848588800993985：与 SETTLE 条件自相矛盾的巨值

**事实**：`state=SETTLE dx=3620848588800993985 dy=-0.9881955606860319`。
SETTLE 的进入条件是 `|dx|≤死区2.0 且 |dy|≤死区2.0`（gimbal_aim.py:127-132），
3.6e18 不可能进 SETTLE。且该值**无小数点/指数** ⇒ 只能是整型（int/numpy 整型）；
而本地源码与 `dist/main_single.py` 的 `update()` 都有 `float(result["dx"])` 强转，
`%s` 打印 Python float 必带小数点或 `e` 指数 ⇒ **本地代码产生不出这个形态**。
**可能原因**：(a) 板端跑的是未同步的旧构建（同一 BUILD_ID 但代码不同）；(b) 某处 numpy
整型泄漏（旧版 deviation/process 未 float 化）；(c) 串口日志本身损坏。
**风险**：若巨值真进了控制律，`JUMP_REJECT_PX=400` 只能挡前 2 帧，第 3 帧起会以
`MAX_STEP_PULSES=80` 的限幅发错误方向指令。
**动作**：① 重新 build + 重烧 + 复测（顺带验证 P0-3 的 (a)）；② 上板打印
`type(dx)` / `raw_u` / `raw_v`；③ 在 `update()` 入口对 dx/dy 加整型→float 强转 +
有限性断言（本地已有，需确认板端同款）。

### P1-2 诊断盲区：`[perf]` 的 stage 被显示层替换，看不到检测器真实 stage

`display_result` 把过期结果整体换成 `{valid:false, stage:"stale"}`，检测器自己的
`stage`（track / roi_search / full_search / no_black_frame）和 `detector_ms` **没有进日志**
（快照 `snapshot["result"]` 里其实有）。现在**无法区分"检测成功但太慢"与"检测失败"**，
而这两种的修法完全相反（前者改性能/新鲜度策略，后者改检测算法）。
**动作**：`telemetry.format_perf_line` 增加 `det_stage=` / `det_valid=` / `det_ms=` 三字段
（数据现成，拼串一行）；注意该函数被 `tools/test_main_self_test.py`
的 `test_perf_log_branch_formatting` 逐字段冻结，需同步更新用例。

### P1-3 级联拖累：主循环 read 5 倍、显示 11.6fps

识别线程吃满 CPU 的连带效应：主循环 `read` 4.2→22.7ms、`draw` 2.1→14.4ms，
显示 29.8→11.6fps、`drop(show)` 0→19667。`loop=32.6ms` 尚未超 66ms 慢线，
但若识别再慢会先把主循环拖过线。修 P0-1 后这些应同步恢复（可作为修复的验证指标）。

### P2 偶发极慢帧：age 在 165→613→504ms 间跳变

检测耗时分布很宽（165ms ~ 613ms+），最慢帧可能 >600ms（Canny 兜底 + 宽半径精修全跑齐）。
对"临界新鲜度"影响极大：偶尔 <200ms 的帧能让 aim 短暂拿到有效测量（见 P0-2 旁证），
但不可依赖。修性能时应看**最坏帧**而非平均帧。

## 5. 根因链（因果）

```text
track 路径不生效（原因待查：full_search 从未成功 / 成功后下帧 track 又失败）
        │
        ▼
每帧都跑 full_search 穷尽搜索（~10 档阈值 × 每候选 verify + 宽半径精修 + 再验，全分辨率）
        │
        ├──► 单帧 ~312ms（detect_fps=3.2）
        │        │
        │        ▼
        │   超过 RESULT_MAX_AGE_S=0.20s ⇒ 结果双层被判 stale
        │        │
        │        ▼
        │   aim 永远收不到有效测量 ⇒ HOLD / lost++ / 云台不动
        │
        └──► CPU 被识别线程吃满 ⇒ 主循环 read 4.2→22.7ms、显示 29.8→11.6fps、
            drop(vision)=32k、drop(show)=19.7k
```

## 6. 建议的修改方向（按执行顺序，供接下来改代码）

**第 0 步（改任何算法之前必须先做）**
1. **核对板端构建 == 本地源码**：`tools/build_single.py` 重新生成 dist → 核对 BUILD_ID
   → 重烧 → 复测 `[perf]`。P1-1 的 dx 巨值只有"板端代码不同"能解释，且它同时决定
   P0-3 是"构建问题"还是"算法问题"。

**第 1 步：补可观测性（一行级改动，决定后续修法）**
2. `[perf]` 增加 `det_stage / det_valid / det_ms`（数据在快照里现成），同步更新
   `test_main_self_test.py` 的字段冻结用例。复测后即可区分 P0-1 的两种成因。

**第 2 步：性能（P0-1，主战场）**
3. 若 det_stage 显示 `full_search` 每帧必跑：考虑给 `_search` 加**提前退出**——
   当前候选一旦验证成功即返回，但阈值档是顺序试的；可记录"哪一档/哪个候选命中"，
   下一帧优先复用（`_locked_th` 已有类似机制，可扩展到候选几何）。
4. 宽半径兜底（REFINE_RADIUS_WIDE=20）目前对**每个失败候选**都跑，成本翻数倍；
   可限制为"仅前 N 个候选"或"仅 roi_search 已局部化时"，需对着
   `tools/test_real_scene.py` 与 `test_performance.py` 确认无回归。
5. 评估 `OPENCV_THREADS`（现为 1）与 `SEARCH_WIDTH`（现为 320）在板端的实测收益；
   `verify/_refine` 跑全分辨率 640×480，可试探"降采样验证 + 全分辨率精修"两级口径。
6. ⚠ 不要动 `SEARCH_EXHAUSTIVE=True` 的稳定性口径去换速度（v0.6.4 刚按用户要求恢复，
   历史教训：有界预算会丢帧）。性能要从"减少每候选成本"上要，不从"少验候选"上要。

**第 3 步：新鲜度策略（P0-2）**
7. `RESULT_MAX_AGE_S=0.20` 是安全闸（过期结果不得驱动电机），不建议简单调大。
   如检测确实慢到 300ms 量级，可评估"按最近一次 `detector_ms` 自适应放宽"
   （如 `max(0.20, 2×det_ms)`）或"SEARCH 寻靶期放宽、TRACK 追踪期严格"的分段策略；
   动前必须想清楚"过期结果驱动云台"的风险边界，并在 README 记录口径变化。

**第 4 步：收尾**
8. P1-1：dx/dy 入口强转 + 有限性断言；板端复现时打印类型与 raw_u/raw_v。
9. 修复验证门禁：`tools/test_performance.py`（29/30、0.803px、0 误检）+
   `tools/test_real_scene.py`（两张固件，第二帧必须走 track）+
   `tools/test_runtime_performance.py` + `check_app.py --manifest`；
   板端复测指标：detect_fps、age、drop(vision) 三项回归健康量级。

## 附：本机截屏不可用的说明（备查）

本机 GDI `BitBlt(GetDC(0))` 与 `PrintWindow(PW_RENDERFULLCONTENT)` 对主屏/副屏/
MaixVision/前台 QQ 窗口**全部返回纯黑**（mean luma=0，nonzero=0.000）；而
`EnumWindows` 正常枚举到全部交互窗口、会话状态 Connected、`OpenInputDesktop` 成功、
双显示器 WMI Active=True、无 LogonUI/屏保进程。结论：本环境的帧缓冲读取被隔离，
无法用截屏方式观察本机屏幕；本文证据全部来自用户提供的截图与日志转录。
